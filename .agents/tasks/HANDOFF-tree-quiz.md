## 1. 목표

조경기능사 실기 **수목감별** 대비용 무료 웹 서비스를 만든다.
- 합격 기준: **이 서비스만으로 공부해도 수목감별을 통과할 수 있어야 한다.**

- 운영 비용은 0원이어야 한다.

## 2. 사용자가 제공한 공식 자료 (작업 위치 루트에 있음)

| 파일 | 용도 |
|---|---|

## 3. 반드시 지킬 제약

### 데이터 출처
- **nature.go.kr의 사진, 텍스트, 데이터는 쓰지 않는다. 스크래핑도 하지 않는다.**
  - 사이트 하단에 All rights reserved와 무단 사용 처벌 문구가 있다.
  - robots.txt가 `/fileUpload/`와 모든 스크래퍼를 차단한다.
- 허용하는 출처: 아래 사이트의 공식 API만 쓴다. 요청 속도를 제한하고, User-Agent에 서비스 이름과 연락처 자리를 넣는다.
  - iNaturalist API: research-grade 관찰만 쓰고, 가능하면 한국 관찰을 우선한다.
  - Wikimedia Commons API
  - GBIF, Wikidata (CC0): 학명, 과, 속, 영명, 한국어 이름
- 허용하는 사진 라이선스: CC0, CC-BY, CC-BY-SA, CC-BY-NC, CC-BY-NC-SA. **ND 계열과 저작권 전부 보유(all rights reserved) 사진은 제외한다.**
- 사진마다 원본 URL, 작성자, 라이선스, 라이선스 URL을 저장한다. 화면에도 사진별 출처를 표시하고, 별도 출처 페이지를 둔다.
- NC 라이선스 사진이 섞이므로 비상업 서비스로만 운영한다. README에 이 점을 명시한다.
- 수종 설명은 새로 쓴다. 시험 대비용 핵심 구분 포인트 위주로 짧게 쓴다(예: 소나무 잎 2개, 리기다소나무 3개, 잣나무 5개). 위키백과 문장은 그대로 옮기지 않는다. 사람이 검수해야 하는 사실은 표시해 둔다.

### 기술
- 정적 사이트로 만든다: Vite + React + TypeScript.
- Cloudflare Pages나 GitHub Pages에 무료로 배포할 수 있게 하고, 배포 설정과 안내를 포함한다.
- 백엔드와 로그인은 없다. 학습 기록은 IndexedDB에 저장한다.
- PWA로 만들어 오프라인에서도 동작하게 한다.
- 의존성 버전은 정확히 고정한다. 스케줄링은 `ts-fsrs`를 쓰고, 버전은 npm에서 최신을 확인한다.

## 4. 수종 데이터 스키마

수종마다 다음 항목을 둔다.
- 국명, 이명/별칭(정답으로 인정), 학명, 영명, 과, 속
- 상록/낙엽, 교목/관목/덩굴
- 형태 특징: 잎, 수피, 꽃, 열매, 겨울눈, 수형
- 개화기, 결실기, 조경 용도
- 혼동 수종 그룹과 구분 포인트
- `photos[]`: 부위 태그(leaf/bark/flower/fruit/whole/winter)와 출처 정보

사진은 수종마다 5~8장, 여러 부위와 계절을 목표로 한다. 4장 미만인 수종은 보고한다.

별칭과 표기 변형 예시: 곰솔 = 해송, 메타세쿼이아 = 메타세콰이어. 공식 목록에 있는 표기를 기본 정답으로 한다.

## 5. 데이터 파이프라인 (`scripts/`, Node + TS)

- 메타데이터와 사진을 API로 받고, 라이선스로 걸러서 WebP로 변환해 정적 자산 폴더에 저장한다.
  - 크기: 긴 변 약 800px, 썸네일도 만든다.
- 결과를 JSON 매니페스트로 쓴다.
- 다시 실행해도 결과가 같아야 하고(idempotent), 중간에 끊겨도 이어서 받을 수 있어야 한다.
- 무료 호스팅 한도(Cloudflare Pages 파일당 25MB, 2만 개)를 넘지 않게 한다.
- 사진 부위 태그는 iNaturalist annotation이나 Commons 분류를 쓰고, 없으면 untagged로 둔다.
- 나쁜 사진은 JSON 플래그로 빼거나 로컬 검수 화면에서 제외할 수 있게 한다.
  - 예: 다른 수종, 표본 사진, 사람, 이름표가 보이는 사진
- **파이프라인을 실제로 돌려서 진짜 데이터가 들어간 상태로 완성한다.**

## 6. 학습 설계 (연구 근거, 모두 구현)

| 근거 | 구현 |
|---|---|
| 인출 연습 (Roediger & Karpicke, 2006) | 읽기보다 퀴즈를 먼저 한다 |
| 간격 반복, FSRS (Ye et al., 2022) | 수종마다 카드를 두고, 매일 새 카드와 복습 카드를 배정한다 |
| 교차 학습 (Kornell & Bjork, 2008) | 순서를 섞고, 헷갈리는 수종을 같은 세션에 일부러 섞는다 |
| 예시 다양성 | 문제마다 사진을 랜덤으로 고르고, 최근 사진은 피하며, 부위를 다양하게 한다 |
| 무작위 출제 | Fisher-Yates 셔플을 쓰고, 같은 수종이 연속으로 나오지 않게 한다. 어떤 모드에도 고정 순서는 없다 |
| 어려운 오답 보기 | 같은 속이나 혼동 그룹에서 먼저 뽑는다 |
| 형식 전환 (Kang, McDermott & Roediger, 2007) | 처음엔 객관식, 익힌 뒤엔 이름을 직접 입력한다. 띄어쓰기는 무시하고 별칭과 표기 변형은 인정한다. 오타에 가까운 답은 "거의 맞음"으로 표시하되, 채점 기준은 설계 때 정한다 |
| 즉시 교정 피드백 (Butler & Roediger, 2008) | 틀리면 정답, 핵심 구분 포인트, 고른 수종과의 사진 비교를 바로 보여준다 |

### 모드
1. **오늘의 학습**: FSRS로 오늘 볼 카드를 정한다.
2. **실전 모의고사**: 실제 시험 형식(사전공개문제 PDF 기준)으로, 이름을 직접 써서 답하고 점수를 낸다.
3. **약점 집중**: 많이 틀린 수종과 헷갈리는 쌍을 모아서 낸다.
4. **도감**: 과, 상록/낙엽, 부위로 검색하고 거를 수 있다. 모바일을 먼저 생각하고, nature.go.kr보다 보기 편하게 만든다.

### 그 외
- 대시보드: 수종별 숙달도, 전체 목록 학습 범위, 합격 가능성(전체 수종의 FSRS retrievability로 추정), 연속 학습일
- 학습 기록 JSON 내보내기와 가져오기 (로그인이 없으므로 필요하다)
- 접근성: 키보드로 퀴즈를 풀 수 있게 하고, 사진에 대체 텍스트를 넣고, 명도 대비를 지키고, 반응형으로 만든다.

## 7. 검증 (필수)

- `npm run build`와 lint를 오류 없이 통과한다.
- `vitest --run` 단위 테스트를 둔다.
  - 셔플과 연속 중복 방지
  - 오답 보기 선택
  - 정답 매칭(별칭, 띄어쓰기)
  - FSRS 세션 구성
  - 합격 가능성 계산
- 개발 서버를 띄워 브라우저에서 확인한다(스크린샷이나 DOM 검사).
  - 모바일과 데스크톱 화면에서 4개 모드가 처음부터 끝까지 동작한다.
  - 사진과 출처가 표시된다.
  - 새로고침해도 학습 기록이 남는다.
  - 확인이 끝나면 개발 서버를 종료한다.
- 데이터 검증 스크립트를 둔다.
  - 공식 목록의 모든 수종에 메타데이터가 있고 사진이 4장 이상이다.
  - 모든 사진에 라이선스와 작성자가 있다.
  - 금지된 라이선스가 없다.
  - nature.go.kr URL이 어디에도 없다.

## 8. 완료 후 대조 (에이전트가 직접 수행)

사용자가 요청한 항목이다. 사용자에게 넘기지 않는다.
1. HWP 공식 목록과 `data/species.json`을 수종 수, 국명, 표기 기준으로 하나씩 비교한다. 빠진 수종, 남는 수종, 표기가 다른 수종을 표로 정리한다.
2. 별칭과 정답 인정 표기가 맞는지 확인한다.
3. 수종별 사진 수, 부위 분포, 라이선스 누락을 확인한다.
4. 수종별로 사진을 샘플로 열어 다른 수종 사진이 섞이지 않았는지 확인한다.
5. 혼동 수종 구분 포인트에 사실 오류가 없는지 확인한다.
6. 문제가 있으면 고치고 다시 대조한다.

정말 구하기 어려운 자료가 있으면 사용자가 직접 구해 줄 수 있다. 필요한 파일 이름과 게시 위치를 `.agents/tasks/needs-from-user.md`에 적고 사용자에게 요청한다.
